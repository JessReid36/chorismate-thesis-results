In phase1_system_dev/spa_prepare.py, the memory column of JOBS (one number per job type):

   job_ts                250 -> 250 gb   (unchanged; measured 197.28 GiB, and its %maxcore 12000 on 16 cores allows
                                          about 188 GiB, so this request is the one that is needed)
   job_ts_freq_irc       250 ->  64 gb
   job_r_irc             180 ->  64 gb
   job_r_irc_freq        180 ->  64 gb
   job_p_irc             180 ->  64 gb
   job_p_irc_freq        180 ->  64 gb
   job_r0                180 ->  64 gb
   job_r0_freq           180 ->  64 gb

This replaces SP_PLAN.txt's "250 GB (TS; TS frequencies + IRC) or 180 GB (minimisations, frequencies)" by "250 GB (TS)
or 64 GB (TS frequencies + IRC, minimisations, frequencies)". Everything else in that sentence - 16 cores, walltime
176 h, e-mail on abort only - stays.

64 gb is 15.6 times the largest memory any of the seven used (4.10 GiB) and 3.05 times the largest virtual memory
(20.99 GiB). PBS enforces the first of these: SP_ERRATUM1.txt A4 records a kill as "mem 221432992kb exceeded limit
125829120kb", a memory figure against a memory limit.

WHAT IS NOT CHANGED, AND THE RISK THAT LEAVES

%maxcore is left as it is: 12000 MB per core for the TS core step, 6000 for the other core and environment steps, 8000
for the frequencies and the IRC. Lowering it would change what ORCA may do, and so could change a number; this
amendment changes only what PBS is asked for. ORCA was nowhere near those ceilings (6000 MB per core on 16 cores
allows about 94 GiB; the optimisations used 2.2 GiB), but the ceiling is still above the new request. If some frame
needed more than 64 GB, PBS would kill that job, its afterok chain would stop, and the frame would be re-run under
SP_AMENDMENT2.txt A2.2, which already governs a machinery stop. That failure is visible and recoverable; it is
accepted here in exchange for the throughput, and if it happens for any frame the record will say so.

A3.3 WHAT IS DONE TO THE JOBS ALREADY IN THE QUEUE

A run folder is handled only if it is untouched: every one of its eight jobs is in state Q or H, and the folder holds
no job output (no job_*.pbs.out) and no step record. For such a folder the eight queued jobs are deleted, the nine
generated files that this amendment changes are replaced (A3.4), and the eight jobs are resubmitted with the same
afterok structure submit.sh uses.

A run folder that is not untouched is left exactly as it is and listed as deferred. That covers a folder with a job
still running - at 11:12 SAST on 21 October, frame 20000 (job_ts 419762, job_r0 419768) and frame 21634 (job_ts
419770) - and a folder in which any job has begun to write. Nothing of a running job is interrupted: SP_PLAN's
discipline is that a run is stopped only when it is clearly not working, and these are working. A deferred folder is
resubmitted by a later bundle once its running jobs have ended and its state is settled, under this same amendment.

The state is read from PBS when the change is applied, not from the state recorded above, so which folders are
untouched may differ by then. A folder in any state this rule does not cover stops the bundle for that folder and is
reported; nothing is guessed.

A3.4 WHAT IS REPLACED IN A RUN FOLDER, AND WHAT IS NOT

Of the 27 files and 9 links a run folder holds, the amended generator changes nine: the eight job_*.pbs and
GENERATOR_LOG.txt, which records their sha256. Every ORCA input (core.inp, env.inp, freq.inp, irc.inp), both start
files, region.txt, starts.sha256, submit.sh and all nine links are byte for byte what is committed, because the change
touches only the memory line of the PBS header. Each job_*.pbs differs from the committed one in exactly one line,
"#PBS -l select=1:ncpus=16:mem=...gb", and the bundle checks that before it replaces anything: a fresh generation into
a scratch folder on hpc1, then a comparison showing that the other 18 files and 9 links are unchanged and that each
job script's only difference is that line. If anything else differs, nothing is replaced.

Replacing those files cannot disturb a running or queued job, because PBS takes its copy of a job script when the job
is submitted; a job already in the queue is unaffected by the file on disk. That is also why the queued jobs have to
be deleted and submitted again rather than altered in place.

A3.5 THIS IS NOT A MACHINERY STOP

Deleting a queued job here is a disclosed correction, as SP_AMENDMENT2.txt A2.2 provides for ("an input error is not
re-run as a machinery stop: A1.5 has the input corrected in a disclosed amendment"). It is none of the machinery stops
A1.5 fixes, which are disk, quota, ORCA input errors and start-file faults. It therefore consumes no frame's single
allowed re-run, and no run folder is renamed _stop1 for it. A frame that later suffers a genuine machinery stop still
has its one re-run.

A2.2 also counts "a job that has left the queue without its last line and without a record for its step" as a
machinery stop, which a deleted job would otherwise satisfy. Two things keep that from being misread. Only untouched
folders are handled, so there is no step record or output for a deleted job to be matched against. And each handled
folder's SUBMITTED is replaced by the new job ids, with the first wave's kept beside it as SUBMITTED.wave1, so the
bundle that later collects the outputs and writes LEFT_QUEUE.txt reads the ids that are really in the queue. The
deleted ids are listed in this amendment's record in package_waves/ and are not jobs of the package any more.

DIRECTION

None on any reported quantity. The calculations, their inputs, their thresholds and their checks are identical; only
the memory asked of the scheduler differs, and in six of the seven cases the ORCA ceiling is unchanged too. No
package result had been read when this was written.
